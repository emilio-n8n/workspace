# ADR-0006 — Serveur MCP officiel

**Statut** : accepté
**Date** : 2026-10-10

## Contexte

Le pilotage d'une suite bureautique par des agents IA est un objectif fondateur du projet, pas une extension tardive. Le risque principal est de créer une seconde logique métier, plus faible en sécurité, qui contourne les permissions de l'application. Le serveur MCP doit donc être un **client privilégié mais bridé** des mêmes services que l'UI.

## Décision

- **Processus séparé** `apps/mcp-server`, deux transports : **stdio** (agents locaux de confiance) et **HTTP streamable** (agents distants, authentifiés).
- **Aucune logique métier propre** : les outils MCP sont des adaptateurs fins qui appellent les mêmes `service.ts` de modules que les server functions web, avec le même type d'`Actor`.
- **Authentification** : jetons (`api_tokens`) émis par l'utilisateur dans l'interface, liés à (utilisateur, organisation), **scopés** par domaine (`drive:read`, `drive:write`, `docs:read`, …), révocables, avec expiration optionnelle, stockés **hachés**, journalisés (`dernier usage`).
- **Principe de moindre privilège** :
  - les scopes `read` sont distincts des scopes `write` ;
  - aucune opération d'administration n'est exposée par défaut ;
  - le jeton ne peut jamais accéder à une ressource que son propriétaire ne voit pas dans l'UI (mêmes `can(actor, …)`).
- **Actions sensibles / destructrices** : chaque outil concerné documente une exigence de confirmation explicite (`confirm: true` + description des conséquences) ; la suppression est réversible quand le produit l'est (corbeille).
- **Audit** : chaque appel journalise acteur (jeton), organisation, outil, paramètres minimaux, ressource visée, résultat. Les refus sont journalisés aussi.
- **Contrats d'outil** : nom stable, schéma d'entrée (JSON Schema), description, scopes requis, erreurs typées — documentés dans `docs/mcp/`.
- **Roadmap d'outils** : v0 en Phase 2 (`files.search`, `files.read`, `docs.read`) ; extension Progressive par module, sous les mêmes règles.

## Conséquences

- Positif : une seule implémentation des permissions, testée une fois ; les agents bénéficient des mêmes données que les humains avec un périmètre strict ; l'audit est centralisé.
- Négatif : le serveur MCP est couplé au démarrage du cœur applicatif (monolithe modulaire) — accepté à ce stade ; la latence des appels passe par la base comme le web.
- Tests obligatoires : jeton révoqué → refus ; scope insuffisant → refus ; autre organisation → refus ; ressource non partagée → refus ; action destructive sans confirmation → refus.

## Alternatives étudiées

| Option | Pourquoi écartée |
|---|---|
| Accès direct des agents à PostgreSQL | Contourne toute la couche d'autorisation — interdit |
| API HTTP publique uniquement (pas de MCP) | Moins utile pour les agents ; l'API publique viendra en plus (Phase 6), pas à la place |
| Un jeton « administrateur » par défaut | Violerait le moindre privilège et protégerait mal les données |
| MCP intégré dans le processus web | Mélange des cycles de vie et des transports ; un processus séparé est plus clair et testable |
